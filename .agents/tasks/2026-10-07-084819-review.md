# P2M-2 Core Physical Dispatch Backend — migration 051 review

A single new migration (`051_dispatch_core.sql`) introduces physical fulfilment: the `dispatches`/`dispatch_lines` header-detail pair, a per-org/year `dispatch_sequences` counter feeding `next_dispatch_number()`, allocation fulfilment tracking (`fulfilled_qty` + `partially_fulfilled` status) grafted onto the existing `stock_allocations` table, the two new `sales_orders` statuses (`partially_dispatched`, `completed`), and the atomic `record_dispatch(uuid, jsonb, text)` RPC that decrements physical stock, writes one `stock_movements` row per line, advances each allocation, and recomputes the order dispatch status — all inside one `BEGIN;…COMMIT;`. The implementation copies the established house patterns from migrations 022/040/042/046/048/050 field-for-field and uses the real existing constraint names when it drops and re-adds CHECKs. Verification is honestly limited to static review plus a frontend build; there is no local Postgres to apply the migration, and the report says so rather than inventing apply results.

Watch for: nothing blocking. The CHECK-constraint surgery preserves every prior value and keeps existing rows valid (confirmed); client-supplied identities cannot be smuggled because org/line/product/location are all derived from the locked allocation and the locked order (confirmed); the lock order sales_orders→stock_allocations→stock_items plus the remaining-quantity guard under row lock closes the concurrent-overdispatch and negative-stock windows (confirmed); `movement_type='dispatch'` is reused with no new ledger and no second audit system (confirmed); and scope is exactly the one migration plus plan/report with nothing committed, staged, or pushed (confirmed).

**Verdict**: APPROVED

## High-level view

The dispatch tables follow the 048 table template precisely: UUID PKs, org/owner FKs, the owner-immutability and `updated_at` triggers reusing the shared `prevent_owner_id_change()`/`update_updated_at()` functions, dedicated `validate_*_org_integrity()` SECURITY DEFINER triggers, RLS enabled with a single member-SELECT policy and SELECT-only grant, and no client write path. The nine `dispatch_lines` FKs carry exactly the ON DELETE rules the brief specified (dispatch_id CASCADE, all others RESTRICT).

The CHECK surgery on `stock_allocations` and `sales_orders` is the riskiest part of any migration like this, and it is done safely. It drops and re-adds the real constraints (`salloc_status_check`, `salloc_open_has_no_terminal_ts`, `so_status_check`) by their actual names, re-lists every previously allowed value, and the two P2L-6 release-path CHECKs (`salloc_released_has_released_ts`, `salloc_fulfilled_has_fulfilled_ts`) are left untouched. Existing rows (`fulfilled_qty=0` default, status open/released/fulfilled/cancelled) satisfy every new constraint, so the re-add cannot fail on live data.

The `record_dispatch` RPC is the trust boundary and it is correct: the client supplies only `{stock_allocation_id, qty_bottles}` per line; org comes from the locked sales order, and line/product/location come from the locked allocation. The lock order is sales_orders (FOR UPDATE) → stock_allocations (FOR UPDATE, iterated in deterministic id order) → stock_items (FOR UPDATE), with a remaining-quantity check (`qty_bottles - fulfilled_qty`) and an independent physical-sufficiency check both evaluated while the rows are locked. A concurrent 60+60 against a 100-bottle allocation serialises on the allocation lock and the second transaction fails.

Physical history reuses the existing ledger: `movement_type='dispatch'` (already in the 040 vocabulary, so no CHECK change), one movement per line, `reference_type='dispatch_line'`/`reference_id=dispatch_line.id`, and the line's `stock_movement_id` back-filled in the same transaction. Audit extends the single shared `audit_log_row_change()` writer with two mappings (26→28) and preserves the fail-closed else branch; there is no second audit system and no second stock ledger. `sales_order_lines.quantity_bottles` is never written, allocation `qty_bottles` is never changed, and allocations are never deleted or recreated.

Scope holds: only `051_dispatch_core.sql` plus the plan and report are present as untracked files, no React/service/page or other migration is touched, `stock_items` gains no reserved/allocated column, and the branch has no commit, staging, or push for this task.

### House-style fidelity vs 040–050

Each structural choice is copied from a named precedent, verified faithful against the on-disk source. `assert_dispatch_actor` is `assert_cellar_actor` (022) with the role array changed to `ARRAY['OWNER','ADMIN','CELLAR','SALES']` and the message adjusted; it is SECURITY DEFINER, pins `search_path = public, pg_temp`, revokes PUBLIC, and is not granted to authenticated — correct for an internal guard. `next_dispatch_number` copies `next_sales_order_number` (046): auth + `is_org_member` check, `INSERT … ON CONFLICT (org_id, order_year) DO NOTHING`, `SELECT last_number+1 … FOR UPDATE`, `UPDATE`, returning `DISP-YYYY-NNNN`; PUBLIC revoked, authenticated granted. `recompute_sales_order_dispatch_status` mirrors `recompute_sales_order_allocation_status` (048): reads status, early-returns outside its own flow set, drives off quantities, updates only on change, assumes the caller holds the order lock, PUBLIC revoked. The integrity triggers mirror `validate_stock_allocation_org_integrity` (048). The ledger INSERT column list matches 040/042 exactly, one movement per touched line. The post-validation `DO $$` block at the tail matches the 046/048/050 style and asserts the full object inventory. The single audit writer is extended, not replaced, with the fail-closed `ELSE NULL → RAISE EXCEPTION` preserved. All seven SECURITY DEFINER functions pin the search_path; `$$` quoting and the single `BEGIN;/COMMIT;` are balanced.

### CHECK-constraint surgery safety

The constraint names used in the DROP/ADD pairs are the real ones from 046 (`so_status_check`) and 048 (`salloc_status_check`, `salloc_open_has_no_terminal_ts`), confirmed against the on-disk migrations. `so_status_check` is re-added as a strict superset: all six originals including the vestigial `allocated` plus `partially_dispatched` and `completed`; `dispatched` is deliberately not added. `salloc_status_check` keeps `open/released/fulfilled/cancelled` and adds `partially_fulfilled`. The terminal-timestamp CHECK is widened to also forbid `released_at`/`fulfilled_at` on `partially_fulfilled`, which an in-flight row never has. The two release-path CHECKs are left verbatim, so P2L-6 release/cancel behaviour is preserved. New quantity-consistency CHECKs (`salloc_open_qty_zero`, `salloc_partial_qty_consistent`, `salloc_fulfilled_qty_full`) and bounds CHECKs (`>= 0`, `<= qty_bottles`) all hold for an existing `open, fulfilled_qty=0` row, so the ADD cannot fail on live data.

### record_dispatch atomicity, lock order, and the trust boundary

The RPC derives `org_id` from the row returned by `SELECT * … FROM sales_orders … FOR UPDATE` and derives `sales_order_line_id`, `finished_product_id`, `location_id` from the row returned by `SELECT * … FROM stock_allocations … FOR UPDATE`. The client payload contributes only the allocation id and the quantity. The allocation is checked to belong to `v_order.id` and to be `open`/`partially_fulfilled`. `remaining = qty_bottles - fulfilled_qty` is computed under the allocation lock and the request is rejected if it exceeds remaining — this is the duplicate-fulfilment guard. The `stock_items` row is then locked and independently checked for physical sufficiency before the decrement, so stock cannot go negative even if a damage/adjustment reduced physical below the reserved amount. Allocations are iterated `ORDER BY (elem.value ->> 'stock_allocation_id')`, giving a deterministic lock order that avoids deadlocks between concurrent dispatches. The `validate_dispatch_line_org_integrity` trigger independently re-asserts the four allocation-identity equalities (order, line, product, location) as defence in depth, so even a hypothetical direct insert could not break the invariants.

### Ledger, audit, and immutability guarantees

Dispatch movements use the pre-existing `'dispatch'` type with `qty_bottles_delta = -qty`, `reference_type='dispatch_line'`, `reference_id = v_line_id`; the line is inserted first to supply the id, the movement is inserted, then `stock_movement_id` is back-filled by UPDATE in the same transaction. No new movement type and no `stock_movements` CHECK change. The allocation update only ever increases `fulfilled_qty`; it never touches `qty_bottles`, never deletes, never recreates. `sales_order_lines.quantity_bottles` is read for the recompute but never written. There is no second audit path (triggers do all audit writes) and no second physical-stock ledger.

No void/Finance/compliance/seed logic exists; `'voided'` is a value-only forward-compat entry with no code path. The report is explicit that the migration was not applied (no local Postgres) and does not fabricate apply results, relying instead on the embedded post-validation block — which is the honest and correct posture for this environment.
